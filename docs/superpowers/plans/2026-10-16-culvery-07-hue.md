# Culvery — Plan 7: Philips Hue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Tasks 1–15 are subagent tasks; Task 16 is the controller on the `culvery-5` AVD with the user and the household's bridge; Task 17 needs the user, the bridge and the son's SM-T510.

**Goal:** One tap turns every light off; Home toggles the main room and opens it on a Lights tab where each Hue room has on/off, brightness and its scenes; and Holiday mode (Adult or Admin PIN) turns the lights off and starts the chosen Hue automations, all against the household's Hue Bridge on the home network.

**Architecture:** A new capability `:capability:lights` owns the `LightsSystem` seam, the saved connection and choices (DataStore `lights_settings`), the bridge's event stream while a lights screen shows (`LightsFollow`), the commands with the brightness drag paced (`LightsActions`), All lights off and Holiday mode as capability functions (`LightsHouse`), the permission `lights.holiday`, the Home card, the Lights tab and Settings › Lights. A new provider `:provider:lights-hue` finds the bridge by mDNS (`NsdManager`), pairs with the link button, and talks CLIP v2 over HTTPS with OkHttp, trusting only Signify's Hue root CA with the bridge id as the certificate's name (or, for a bridge that doesn't chain to it, the certificate seen at pairing); it parses with a plain-JVM `HueJson` on kotlinx.serialization. The home-network rule and the percent slider Music already has move to `:core:plugin` and `:core:ui` first, so both capabilities share them without seeing each other.

**Tech Stack:** Kotlin 2.2.20, Jetpack Compose (BOM 2025.09.00), Hilt 2.57.1, DataStore 1.2.1, Coroutines 1.10.2, OkHttp 4.12.0 (+ MockWebServer 4.12.0), kotlinx-serialization-json 1.9.0 (already in the catalogue, as `:provider:calendar-google` uses it), `javax.net.ssl` / `java.security.cert`, `android.net.nsd.NsdManager`, `WifiManager.MulticastLock`, `ConnectivityManager.activeNetwork`; JUnit4 + Robolectric 4.16 + Truth + Turbine, Roborazzi 1.46.1; the JDK's `keytool` for the test certificates. **No new library.**

**Ask the user before Task 8 and before Task 11** (each is a stop until answered; the controller asks, not a subagent):
- **Task 8, the Hue root CA file.** It is published in Hue's developer documentation ("Using HTTPS"), which needs a developer sign-in. Fetching it is a download: ask the user to supply the PEM, or for permission to fetch it, naming the file, its source and its size (about 1 KB). Without it, Task 8 builds both routes with the test CA and the bundled file is added before Task 16.
- **Task 11, deprecated NSD calls.** The tablet runs Android 11 (API 30). There, the only way to resolve an mDNS service is `NsdManager.resolveService(NsdServiceInfo, ResolveListener)` and to read its address `NsdServiceInfo.getHost()`, both deprecated in API 34 (replaced by `registerServiceInfoCallback` and `getHostAddresses`, API 34+). The house rule is never a deprecated API without asking. Options for the user: (a) the new calls on API 34+ and the deprecated ones below, each `@Suppress("DEPRECATION")` with a one-line reason; (b) skip `NsdManager` and send the DNS-SD question for `_hue._tcp.local` on a multicast socket, as `SonosDiscovery` does SSDP (plain JVM, no deprecated call, but not what spec §3.2 names). The plan is written for (a); (b) changes only `HueDiscovery.kt` and its test.

## Rulings against the code

Where the spec leaves a choice open, or doesn't fit the code at e1cc80c. Each is the plan's call unless it cites the spec.

1. **`isHomeNetworkHost`, `ipv4Parts` and a typed-address helper move to `:core:plugin`** (`HomeNetwork.kt`): the module rules let a capability depend only on core and its own family, so Lights can't use Music's. Music's `speakerHost(typed)` becomes `homeNetworkHost(typed)` in core, the same rule; Music's callers change their import only.
2. **Music's `VolumeSlider` moves to `:core:ui` as `HhPercentSlider`**, gaining `onDrag: ((Int) -> Unit)?` (each change while dragging) beside `onLetGo` (the old `onVolume`). Music passes no `onDrag`; its images don't change. Lights' brightness slider is the same control.
3. **`LightsSystem` carries more than the spec's list**, as `MusicSystem` does: `problem: StateFlow<LightsProblem?>`, `readAll()`, `stream(): Flow<Unit>` (the capability decides when, §4.2; the provider reads), `allOff(leaveOut)` (the provider knows the whole-home group and which lights are in no room, §4.4), and `useAddress(address)`. `rooms` is a `StateFlow`. **A second seam, `LightsProvider`** (`descriptor`, `find()`, `check(address)`, `pair(bridge)`, `open(link, onMoved)`), lets Settings › Lights find and pair a bridge without knowing Hue.
4. **The connection is the DataStore file `lights_settings`**, as Music's `music_settings`: provider id, bridge id, address, application key, the certificate pin (ruling 12), the main room id, the left-out room ids, the Holiday mode automation ids and Holiday mode's on/off (§3.3). Under `files/datastore/`, which 4e's rules already exclude from cloud backup and device transfer (`NoBackupTest` pins every domain), so §3.4 needs no new rule. **Pairing with a different bridge id clears the room and automation choices and sets Holiday mode off**; a new address for the same bridge keeps them. Its flows use `retryWithBackoff` (the Plan 6 follow-up for Music and Door).
5. **"Home or the Lights tab shows" is the Home card or the Lights tab composed**, counted by `LightsFollow.watch()` as `MusicChecks.watch()` does, with `AlertHost.inFront`. While watched: a full read, then the stream, as one flow on `retryWithBackoff` (it reopens with its 1 s … 60 s backoff and reads again on each open, §4.2), and a full read every 60 seconds beside it. The stream ending cleanly counts as a drop.
6. **The brightness drag is paced in `LightsActions`, not the slider:** while dragging, the first value goes at once, then at most one every 300 ms per room, the latest value each time; letting go sends at once and drops any value still waiting (§4.3). Slider range 1–100; off is the switch's.
7. **`HuePacer` keeps at least 100 ms between any two commands to the bridge** (Hue's guidance: about ten a second to lights). Hue's guidance for group commands is about one a second; the spec's 300 ms drag already exceeds it, so Task 16 checks that the bridge never refuses a drag or a paced All lights off (HTTP 429 or 503) and the gap grows if it does.
8. **All lights off counts what didn't turn off as rooms**: each room whose command failed, plus one for all the lights in no room together if any of them failed (§4.4 "every light except the rooms left out"). The line is "1 room didn’t turn off. Try again." for one. The whole-home command refused is "Hue didn’t do that. Try again."
9. **Holiday mode off when an automation refuses to stop:** Holiday mode stays on and says "Hue didn’t do that. Try again." (§6's refused line). Off is saved only when every chosen automation still on the bridge was disabled.
10. **"Started" is the instance's `status` reading `running`** within 5 seconds, read back every second (§4.5), until protocol check 1 says otherwise; the tests label it as unconfirmed. Two or more not started: their names joined with ", " and " and ".
11. **The PIN is asked in `LightsActions`, not `LightsHouse`:** the later whole-app Holiday mode calls `LightsHouse.setHoliday(on)` behind its own PIN. Refusal is `Refusal.InPad` (a Child's PIN: "That PIN can’t do this. Ask a grown-up.", the pad asks again).
12. **TLS (§3.2):** every call trusts either the bundled Hue root CA with the leaf's common name equal to the bridge id (case ignored), or, when the saved connection has a pin, exactly the certificate with that SHA-256 and that name. The hostname check is the same name rule (the bridge has no DNS name). **At pairing:** the bridge id comes from the mDNS record's `bridgeid` or `GET /api/config` (§3.2's unauthenticated source); the first look at `/api/config` tries the CA route; only if the chain doesn't verify does a second look record the leaf, whose name must still be the bridge id, as the pin. Nothing secret is sent before the trust is decided; the pairing `POST` and every later call use it. No trust-all route.
13. **What may be contacted:** a home-network host (ruling 1) on port 443, nothing else; `HueClient` refuses any other address before sending (`NotABridge`, an I/O failure, so a bad saved address leads to a search). An mDNS answer counts only when its address passes the rule. Tests that run a bridge on localhost pass their own accept rule.
14. **The automatic search runs at most once every 30 seconds** (as Sonos's rescan): §4.1's "searches once by itself" on the first failure; later failures within 30 s report at once.
15. **"A different bridge answers at the address"** shows as the name check failing, or `/clip/v2/resource/bridge`'s `bridge_id` differing at a full read: the search runs first; if it finds the saved bridge elsewhere, that is a move; otherwise the problem is `OTHER_BRIDGE`. A 403 is `UNPAIRED` with no search.
16. **Lights in no room** (for §4.4) are `light` resources whose `owner.rid` (a device) is no room's child. **A room can dim** when any of its lights has `dimming`. So the full read also reads `light`, beyond §3.2's list.
17. **The stream's events:** `grouped_light` `on`/`dimming` and `scene` `status` updates are applied as they come; any `add` or `delete` event, or an update to a `room`, reads everything again at once.
18. **The › on the main-room button** sets `LightsView.focus` to that room and opens the Lights tab; the tab scrolls to it and clears `focus`.
19. **Settings › Lights is page id `lights`, order 470** (§5.3; Music 450, Door 500). **The Home card is `lights.home`, REGULAR, priority 20**, after Music's 30; with Today, Coming up, the forecast and Music all shown, the placer drops it (§5.1).
20. **Pairing:** Find Hue Bridge uses the first bridge the search hears; the pairing sheet asks every 2 seconds for 30 seconds (§4.1) and is drawn on `OverlayHost` with `closesWhenIdle = false` while it waits. A typed address is four numbers in a private range, as Music's.
21. **The capture switch (§8.2)** is `adb shell setprop log.tag.HueCapture DEBUG`. `HueCapture` exists in `src/debug` (redacts with `HueJson.redact`, logs at debug) and `src/release` (does nothing); `HueCaptureSourceTest` keeps the release one empty. The redaction replaces every `name`, `username`, `clientkey`, `bridgeid`, `bridge_id`, `mac`, `ipaddress`, `gateway`, `netmask` value and any IPv4 literal.
22. **Logs:** `LightsActions` and `LightsHouse` log `"${command.name} failed (${e::class.simpleName})"` with an enum `LightsCommand` (`command.name` is already in `LogHygiene.ALLOWED`). Nothing logs a room, scene or automation name, an address, a bridge id or the key (§6).
23. **`HuePairing`'s `devicetype` is `culvery#tablet`** and `generateclientkey` is `true` (§3.2); the answer's `username` is the key; `clientkey` is not kept (no entertainment streaming).
24. **Offline** is Android's answer when a call fails (`ConnectivityManager.activeNetwork == null`), without a search, as Sonos's `AndroidNetwork`.
25. **`Http.kt` (`Call.await(maxBytes)`) and `AndroidNetwork` are copied from `:provider:music-sonos`**, not shared: no core module has OkHttp, and a provider can't depend on another family. Task 17 adds a follow-up line for a shared network module.
26. **Timeouts:** 3 s connect, read and whole call for reads and commands (§6); the stream has 3 s to connect and no read or call timeout (the 60-second full read notices a dead bridge). No redirects, no retry on connection failure. An answer over 4 MB is a failed call.
27. **`Capability.order`'s KDoc** ("Lights 20, Music 30, Climate 40, Security 50") is brought up to date: Calendar 10, Music 30, Lights 40, Door 50, Weather 60.

Nothing in this plan needs a deprecated API except the question before Task 11. Flagged and avoided: `ConnectivityManager.getActiveNetworkInfo()` (use `activeNetwork`), `RequestBody.create(MediaType, String)` and `MediaType.parse` (use `toRequestBody`, `toMediaType`), `Modifier.semantics { invisibleToUser() }` (use `hideFromAccessibility()`). If the compiler shows a deprecation warning on a line you wrote, **stop and ask**.

## Review Focus

The five failure modes the spec implies, most likely to bite the household, that the spec's own test list doesn't cover; each is pinned by a test in its owning task:

1. **Someone drags the brightness slider of a room that's off, then lets go between two 300 ms steps.** Expected: the room comes on at the value let go, not at the last value the pacing sent, and nothing is sent after the release.
   - Task 5 `LightsActionsTest.theValueLetGoIsTheLastSent`; Task 10 `HueSystemTest.brightnessOnARoomThatIsOffTurnsItOnAtThatBrightness`.
2. **The router gives the bridge a new address overnight.** Expected: the next read finds the bridge again by search, saves the new address, keeps the key, and no status line ever shows.
   - Task 10 `HueSystemTest.aMovedBridgeIsFoundAndSavedWithoutAProblem`; Task 3 `BridgesTest.aNewAddressForTheSameBridgeKeepsTheOpenSystem`.
3. **Holiday mode tapped while the bridge is down, or the Wi-Fi drops halfway.** Expected: down before anything is sent, Holiday mode stays as it was and nothing is saved; a drop after the lights went off is "on", with the line saying what didn't happen.
   - Task 6 `LightsHouseTest.anUnreachableBridgeChangesNothing` and `LightsHouseTest.aDropAfterTheLightsWentOffIsOnWithTheLine`.

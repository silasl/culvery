# Culvery — Plan 7: Philips Hue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Tasks 1–16 are subagent tasks; Task 17 is the controller on the `culvery-5` AVD with the user and the household's bridge; Task 18 needs the user, the bridge and the son's SM-T510.

**Goal:** One tap turns every light off; Home toggles the main room and opens it on a Lights tab where each Hue room has on/off, brightness and its scenes; and Holiday mode (a fresh Adult or Admin PIN) turns the lights off and starts the chosen Hue automations, all against the household's Hue Bridge on the home network.

**Architecture:** Shared pieces move into core first: the home-network rule and the percent slider (`:core:plugin`, `:core:ui`), and a new `:core:net` holding the answer-reading helper, the network check and the multicast lock that Sonos already has. A new capability `:capability:lights` owns the `LightsSystem` seam, the saved connection and choices (DataStore `lights_settings`), the bridge's event stream while a lights screen shows (`LightsFollow`), the commands with the brightness drag paced (`LightsActions`), All lights off and Holiday mode as capability functions run one at a time (`LightsHouse`), the permission `lights.holiday` (fresh PIN), the Home card, the Lights tab and Settings › Lights. A new provider `:provider:lights-hue` finds the bridge by mDNS (`NsdManager`), pairs with the link button, and talks CLIP v2 over HTTPS with OkHttp, trusting only Signify's Hue root CA with the bridge id as the certificate's name; it parses with a plain-JVM `HueJson` on kotlinx.serialization, and paces commands to Hue's guidance with the newest command for a room or light replacing a waiting one.

Music's images don't change. **`HhChoiceChip` gains `spokenName: String? = null`** (its content description when the spoken words don't start with the label), for the scene chips (§5.4); Music's images don't change.
3. **`LightsSystem` carries more than the spec's list**, as `MusicSystem` does: `problem`, `readAll()`, `stream(): Flow<Unit>` (the capability decides when, §4.2), `allOff(leaveOut): AllOffResult` (the provider knows the whole-home group and the lights in no room, §4.4), `useAddress(address)`. **`LightsProvider`** (`descriptor`, `find()`, `check(address)`, `pair(bridge)`, `open(link, onMoved)`) lets Settings › Lights find and pair without knowing Hue.
4. **The connection is the DataStore file `lights_settings`**: provider id, bridge id, address, application key, the main room id, the left-out room ids, the Holiday mode automation ids, Holiday mode's on/off, and **the ids Culvery started** for it (§3.3, §4.5). Under `files/datastore/`, which 4e's rules exclude from cloud backup and device transfer (`NoBackupTest` pins every domain): no new rule (§3.4). **Pairing with a different bridge id clears the room and automation choices, the started ids, and sets Holiday mode off.** Its flows use `retryWithBackoff`.
5. **"Home or the Lights tab shows" is the Home card or the Lights tab composed**, counted by `LightsFollow.watch()` as `MusicChecks.watch()` does, with `AlertHost.inFront`. While watched: a full read then the stream, as one flow on `retryWithBackoff` (reopen with its backoff; read again on each open, §4.2), and a full read every 60 seconds beside it. A stream that ends cleanly is a drop.
6. **The 300 ms drag pacing is in `LightsActions`:** while dragging, the first value goes at once, then at most one every 300 ms per room, the latest each time; letting go sends at once and drops any value waiting (§4.3). Slider range 1–100; off is the switch's.
7. **`HuePacer` paces to Hue's guidance (§4.3):** group commands (`grouped_light`, `scene`) at least 1 000 ms apart, light and automation commands at least 100 ms apart; **a command waiting its turn is replaced by a newer one for the same target** (the replaced caller returns as superseded, not failed); `dropWaiting()` drops every waiting room and light command, and All lights off calls it first.
8. **All lights off counts what didn't turn off as rooms:** each room whose command failed, plus one for the lights in no room together if any failed. "1 room didn’t turn off. Try again." for one. The whole-home command refused is "Hue didn’t do that. Try again." **Left-out ids no longer on the bridge are dropped first**; none left is as nothing left out (the whole-home command).
9. **Holiday mode off when an automation won't stop** (the read-back still shows it on, or the bridge refuses): Holiday mode stays on, that id stays recorded, and the line is "Hue didn’t do that. Try again." Off is saved only when every recorded automation still on the bridge is confirmed off.
10. **Automations (§4.5, confirmed):** a `behavior_instance` whose script is Mimic presence (`script_id` the PM script's, matched by the script's name `PM` from `behavior_script`, or by `state.pm_state` being present: Task 7 decides from the fixture which is reliable and the capture confirms it in Task 17) is on when `state.pm_state == "started"`, started by `{"trigger":{"start":true}}`, stopped by `{"trigger":{"stop":true}}`. Any other is on when `enabled`, switched by `{"enabled":…}`. **After each switch: up to 6 reads, `READ_BACK_MS` (1 s) apart**; confirmed when the read shows the asked state. `AutomationResult { CONFIRMED, NOT_CONFIRMED }`.
11. **The PIN and the token:** `LightsActions` asks `access.authorise(LightsPermissions.HOLIDAY, refusal = Refusal.InPad)`; `lights.holiday` is a fresh-PIN permission, so the pad shows every time. `LightsHouse.toggleHoliday(by: Authorised)` and `setHoliday(on, by: Authorised)` `require(LightsPermissions.HOLIDAY in by.granted)`: the later whole-app Holiday mode passes its own `Authorised`. `allOff()` needs none.
12. **TLS (§3.2, confirmed): the CA route only.** Every paired call trusts the bundled Hue root CA, with the leaf's common name equal to the bridge id (case ignored), checked **only in the trust manager**, which throws `WrongBridgeCertificate : CertificateException`; the hostname verifier accepts because each client's trust manager is built for one bridge id. `HueClient` maps an `SSLHandshakeException` with `WrongBridgeCertificate` in its cause chain to `WrongBridge` (an `IOException`). **Before pairing**, `/api/config` is read through a CA-only trust manager (the chain, no name yet) and the handshake's leaf name must then equal the answer's `bridgeid` (and the mDNS `bridgeid` when there is one), else `WrongBridge`. Nothing secret goes through it.
13. **What may be contacted:** a home-network host (ruling 1) on port 443; `HueClient` refuses any other address before sending (`NotABridge`). mDNS answers count only when their address passes. Tests on localhost pass their own accept rule.
14. **The automatic search runs at most once every 30 seconds** (as Sonos's rescan).
15. **A different bridge at the address** is `WrongBridge`, or `/clip/v2/resource/bridge`'s `bridge_id` differing at a full read: the search runs; **the bridge counts as moved only after a TLS-verified successful read at the candidate address**, and only then is `onMoved` called; otherwise the problem is `OTHER_BRIDGE`. A 403, or an `unauthorized user` error in any answer, is `UNPAIRED` with no search.
16. **Lights in no room** are `light` resources whose `owner.rid` is no room's child; **a room can dim** when any of its lights has `dimming`. So the full read also reads `light`.
17. **The stream's events:** `grouped_light` `on`/`dimming` and `scene` `status` updates applied as they come; any `add` or `delete`, or a `room` update, reads everything again. The SSE parser skips `:` comment lines and `id:` lines.
18. **The › on the main-room button** sets `LightsView.focus` to the room and opens the Lights tab; the tab scrolls to it and clears `focus`.
19. **Settings › Lights is page id `lights`, order 470** (§5.3). **The Home card is `lights.home`, REGULAR, priority 45** (R1): after Today 100 and Coming up 50, before the forecast 40 and Music 30, so with all five the forecast is dropped (§5.1).

21. **The capture switch (§8.2)** is `adb shell setprop log.tag.HueCapture DEBUG`; `HueCapture` in `src/debug` (redacts, logs at debug) and `src/release` (does nothing), `HueCaptureSourceTest` keeping the release one empty. **Redaction (S9):** the values of `name`, `username`, `clientkey`, `bridgeid`, `bridge_id`, `replacesbridgeid`, `mac`, `mac_address`, `ipaddress`, `gateway`, `netmask`, `proxyaddress`, and, by value shape anywhere, a 16-hex bridge id, a MAC address and an IPv4 literal.

## Review Focus

The five failure modes the spec implies, most likely to bite the household, that the spec's own test list doesn't cover; each is pinned by a test in its owning task:

1. **Holiday mode tapped twice, or All lights off tapped during it, while an automation is still being read back.** Expected: one run; the second tap is ignored; the button says "Turning on…"; the next tap after the run turns it off, decided from what was saved.
   - Task 6 `LightsHouseTest.aSecondTapDuringTheReadBackIsIgnored` and `LightsHouseTest.theToggleIsDecidedFromTheSavedRecord`.
2. **An automation that was already running before Holiday mode, or one unticked while Holiday mode is on.** Expected: one already on is never stopped by Holiday mode off; one Culvery started is stopped even if unticked meanwhile.
